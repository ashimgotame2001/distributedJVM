# AGENTS.md — Human-Style Code & Commit Guidelines

Instructions for any AI coding agent working in this repository. The goal is
simple: **produce code and commits that are indistinguishable from those of a
thoughtful, experienced human engineer.** No robotic patterns, no AI "tells,"
no boilerplate noise. Write like someone who owns this codebase.

> Rename this file to match your tool if needed (`CLAUDE.md`, `.cursorrules`,
> `.github/copilot-instructions.md`, etc.). The rules below are tool-agnostic.

---

## 1. Core principle

Write the code a senior engineer on this team would write on a normal day —
clear, idiomatic, and no more clever than it needs to be. When in doubt, match
what already exists in the codebase over any personal or default style.

Read a few nearby files before writing. Mirror their naming, structure,
formatting, error handling, and level of commenting. Consistency with the repo
beats consistency with your defaults.

---

## 2. How to write code (humanized)

### Do

- **Match the surrounding style.** Indentation, quotes, import ordering, naming
  conventions — copy the file you're editing, not a generic template.
- **Name things naturally.** `userCount`, `retryDelay`, `parseConfig()` — short,
  precise, domain-accurate. Avoid ceremony like `dataObject`, `resultValue`,
  `myFunction`, `handleTheThing`.
- **Comment the *why*, sparingly.** A comment should explain a non-obvious
  decision, a tricky edge case, or a link to context. If the code already says
  what it does, don't narrate it.
- **Keep changes focused.** Touch what the task needs. Don't reformat unrelated
  lines, reorder imports repo-wide, or "tidy up" code you weren't asked about.
- **Handle errors where they matter.** Catch what you can actually recover from;
  let the rest propagate. Real messages, real context.
- **Prefer the boring, idiomatic solution.** Use the language's and framework's
  standard patterns. Introduce an abstraction only when there are ≥2 real call
  sites for it.
- **Leave the code runnable.** No placeholder stubs, no `# your logic here`, no
  half-finished scaffolding committed as if done.

### Don't (common AI "tells" to avoid)

- ❌ Docstrings or comments on every trivial function
  (`# This function adds two numbers`).
- ❌ Redundant narration (`// Loop through the array`,
  `// Return the result`).
- ❌ Over-defensive code — wrapping everything in `try/catch`, null-checking
  values that can't be null, validating inputs a caller already guarantees.
- ❌ Over-engineering — factories, interfaces, config layers, and "flexibility"
  for requirements that don't exist yet.
- ❌ Restating the prompt in comments (`// As requested, implement the parser`).
- ❌ Emoji, decorative banners, or `====== SECTION ======` dividers in source.
- ❌ Renaming or rewriting working code just to impose a different style.
- ❌ Inventing files, configs, or dependencies that weren't asked for.
- ❌ Dumping huge explanatory comment blocks a human would never write inline.

### A quick smell test

Before finishing, reread the diff and ask: *"Would a reviewer be able to tell a
machine wrote this?"* If the answer is yes — too many comments, too much
boilerplate, unnatural naming, needless abstraction — trim it down.

## 3. How to commit (human format)

Commit like a person who cares about the git history the next engineer will read.

### Commit structure

- **One logical change per commit.** Don't bundle a bugfix, a refactor, and a
  new feature together. Split them.
- **Atomic and buildable.** Each commit should compile and pass tests on its
  own where practical.
- **Stage deliberately.** Commit the files relevant to the change, not a blanket
  `git add .` that sweeps in unrelated edits.

### Commit message format

Follow the standard git convention:

```
<short summary in imperative mood, ≤50 chars>

<optional body: wrap at ~72 chars. Explain WHY the change was
made and any context or trade-offs. Skip it for trivial changes.>

<optional footer: issue refs, breaking-change notes>
```

**Rules for the message:**

- **Imperative mood, present tense:** "Add retry logic", "Fix null check",
  "Remove dead config" — not "Added", "Fixes", or "Adding".
- **Summary line is a real summary**, not a file list. `Fix race in cache
  eviction`, not `Update cache.go`.
- **Body explains the why**, only when it isn't obvious. Cause, reasoning,
  trade-off, or a link — not a restatement of the diff.
- **Reference issues naturally:** `Closes #142`, `Refs #98` in the footer.
- **Keep it plain.** No emoji, no decorative prefixes, no marketing tone.

### Write commits like a human, not a bot

- ❌ Don't append AI/tool attribution footers, "Generated by…" lines, or
  co-author trailers unless this repo's policy explicitly requires them.
- ❌ Don't list every changed file in the message — that's what the diff is for.
- ❌ Don't write essays for a one-line change, or `Update code` for a big one.
- ❌ Don't use conventional-commit prefixes (`feat:`, `fix:`) unless the repo
  already uses them — then follow suit exactly.
- ✅ Do write the way the existing `git log` reads. Run `git log --oneline -20`
  and match its voice, length, and conventions.

### Good vs. bad examples

**Good**
```
Fix off-by-one in pagination offset

The offset was computed from page*size instead of (page-1)*size,
so page 1 skipped the first record. Adjust and add a regression test.

Closes #204
```

**Bad**
```
🤖 Update pagination.js and pagination.test.js

Added code to fix the pagination as requested by the user. This commit
modifies the offset calculation logic and also adds a new test file to
verify the behavior works correctly.

Generated with AI assistance
Co-authored-by: assistant <bot@example.com>
```

---

## 4. Before you commit — checklist

1. Diff reviewed; no stray debug prints, commented-out code, or TODO stubs.
2. No unrelated files or formatting churn included.
3. Code matches the style of the files around it.
4. Comments earn their place (why, not what).
5. Tests updated/added and passing.
6. Commit is one logical change with a clear, imperative message.
7. Message matches the tone of the existing `git log`.
